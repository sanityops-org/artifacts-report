### Underlying implementation (`word_document_server/tools/content_tools.py`, fetched verbatim)

```python
async def add_heading(filename: str, text: str, level: int = 1,
                      font_name: Optional[str] = None, font_size: Optional[int] = None,
                      bold: Optional[bool] = None, italic: Optional[bool] = None,
                      border_bottom: bool = False) -> str:
    """Add a heading to a Word document with optional formatting.

    Args:
        filename: Path to the Word document
        text: Heading text
        level: Heading level (1-9, where 1 is the highest level)
        font_name: Font family (e.g., 'Helvetica')
        font_size: Font size in points (e.g., 14)
        bold: True/False for bold text
        italic: True/False for italic text
        border_bottom: True to add bottom border (for section headers)
    """
    filename = ensure_docx_extension(filename)
    # Ensure level is converted to integer
    try:
        level = int(level)
    except (ValueError, TypeError):
        return "Invalid parameter: level must be an integer between 1 and 9"
    # Validate level range
    if level < 1 or level > 9:
        return f"Invalid heading level: {level}. Level must be between 1 and 9."
```

## Evaluation Dimensions

### 1. Schema Completeness
- [ ] The tool exposes a concrete input schema generated by FastMCP from the function signature and type hints (`filename: str`, `text: str`, `level: int = 1`, optional formatting fields)
- [ ] Types are accurate (`str`, `int`, `bool`) and required vs optional is derivable (`filename`/`text` required; `level` defaulted; the rest are `None`-defaulted)
- [ ] Defaults are declared inline (`level=1`, `border_bottom=False`)
- [ ] The `level` value range (1–9) is enforced in the handler with an explicit validation branch

### 2. Description Clarity
- [ ] The tool has a title (`Add Heading`) via `ToolAnnotations`
- [ ] The docstring is the tool description and includes an `Args:` block documenting every parameter
- [ ] Each parameter is described with an example where useful (`'Helvetica'`, `14`, "1-9, where 1 is the highest level")

### 3. Integration Compatibility
- [ ] Registered through FastMCP (`@mcp.tool(annotations=ToolAnnotations(...))`), producing a standard MCP tool
- [ ] FastMCP derives the JSON Schema from the annotated Python signature, so the schema is consumable by MCP clients and function-calling LLMs
- [ ] Provides `ToolAnnotations` (`title`) for client-side display

### 4. Example Quality
- [ ] Parameter docs include concrete examples (`'Helvetica'`, font size `14`)
- [ ] The semantic meaning of `border_bottom` is explained ("for section headers")
- [ ] The `level` range and its ordering are documented ("1-9, where 1 is the highest level")

### 5. Extensibility
- [ ] A thin registered wrapper delegates to a reusable implementation (`content_tools.add_heading`), separating the MCP surface from the document logic
- [ ] Tools are grouped by concern into modules (`document_tools`, `content_tools`, `format_tools`, ...) registered in one `register_tools()` function
- [ ] The `border_bottom` default and level validation are applied consistently in the implementation, not the wrapper

## Test Suggestions

### Positive Test Cases
1. Issue "add a heading titled 'Introduction' to report.docx"; verify `add_heading` is called with `filename: "report.docx"`, `text: "Introduction"` (level defaults to 1).
2. Issue "add a level-2 heading 'Methods' in Helvetica at 14pt"; verify `level: 2`, `font_name: "Helvetica"`, `font_size: 14`.
3. Issue "make the section header bold with a bottom border"; verify `bold: True` and `border_bottom: True`.

### Boundary Test Cases
1. `level` at the minimum (1) and maximum (9); verify acceptance, and that `level: 0` or `level: 10` returns the documented validation message.
2. `filename` without a `.docx` extension; verify `ensure_docx_extension` normalises it.
3. `border_bottom` omitted; verify the default (`False`) is applied.
4. `level` supplied as a decimal string (e.g. `"2.5"`); observe the `int(level)` coercion and validation behaviour.

### Negative Test Cases
1. Call with no `filename` or `text`; verify the generated schema / function signature rejects the call (required parameters).
2. `filename` pointing at a non-existent document; verify the tool returns "Document ... does not exist" rather than failing silently.
3. A request to write into a read-only document; verify the writability check returns an error message.
4. A request that conflates headings with paragraphs ("add a new page with a title"); verify the model chooses between `add_heading` and `add_paragraph`/`add_page_break` appropriately.
