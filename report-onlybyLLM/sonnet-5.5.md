# GPT Researcher 多智能体套件:缺陷 / 权限 / 显性风险检查

**统计:共 22 项。P0:4 项,P1:10 项,P2:8 项。**

说明:我已通读全文,并对照原文复核了每一条。文档自称是"文档摘要+代码结构分析",不是源码。因此下面是对文档里逻辑工件的审查,不代表实际代码一定有这些问题。

## P0(4 项,会直接导致错误结果或安全事故)

| #   | 类别    | 概要                                                              | 可能影响                                               |
| --- | ----- | --------------------------------------------------------------- | -------------------------------------------------- |
| 1   | 权限/风险 | Human 节点超时 24 小时后"默认批准"。                                        | 无人审核时,未经验证的内容会自动进入后续阶段或发布。这会让人工把关形同虚设,在高风险报告里尤其危险。 |
| 2   | 缺陷    | Reviewer→Revisor 循环没有最大迭代次数和终止条件。Revisor 只写"重大修改则重审"。           | 可能死循环,成本和 token 持续消耗。评分一直低于 7 时流程无法收敛。             |
| 3   | 权限    | `local_document_search` 的 `doc_path` 是任意字符串,没有目录白名单、沙箱或路径规范化。   | 存在路径穿越风险。可能读取本机敏感文件,再把内容写进报告并发布出去,造成数据泄露。          |
| 4   | 风险    | 网页和本地文档内容没有提示注入防护。Researcher 直接读取外部内容,又同时持有检索和写作工具,且状态由所有智能体共享。 | 恶意网页可以操控 Researcher 的行为,甚至污染整条链路,导致输出被篡改或信息外泄。     |

## P1(10 项,功能缺失或存在明显一致性、安全隐患)

| #   | 类别  | 概要                                                                                                                                                      | 可能影响                                        |
| --- | --- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| 5   | 缺陷  | 文档中的阶段数不一致。"5 阶段工作流"从未定义,而 `current_phase` 有 7 个取值,Chief Editor 的工具有 5 个。                                                                               | 状态流转无法对照验证,评测维度"Workflow Completeness"无从评分。 |
| 6   | 缺陷  | Chief Editor 的工具(`init_research`、`plan_sections`、`run_research`、`review_draft`、`compile_report`)没有 Tool Schema。文档中的 3 套 Schema 与这些工具不匹配。                | 工具调用无法校验,实现时只能猜参数。                          |
| 7   | 缺陷  | Researcher 的工具 `conduct_research` 和 `write_draft` 与 Schema 里的 `web_search`、`local_document_search` 对不上。                                                 | 工具名不一致,可能调用失败或幻觉出不存在的工具。                    |
| 8   | 缺陷  | Reviewer 的输出格式有两种。Prompt 里是含 5 项细分分数的 JSON,Schema 里的 `evaluate_draft` 只返回一个 `score` 和一个 `feedback`。标准名也不一致:`coherence` 与 `sources` 对应 `source_quality`。 | 下游解析失败,评分数据丢失。                              |
| 9   | 缺陷  | 评分类型不一致。Prompt 里的 `overall_score` 是整数,Schema 里是 number(1–10),State 里是 `Dict[str,int]`。"低于 7"这个阈值也写死在 Prompt 里。                                          | 小数分值会被截断,可能误判通过或不通过。阈值无法配置。                 |
| 10  | 缺陷  | 配置里 `max_sections=3`,Editor 要求 3–5 节,压力测试又用 `max_sections=10`。                                                                                          | 配置冲突。超出 5 节的情形没有定义。                         |
| 11  | 缺陷  | Writer 要求全文 1500–2500 词,Executive Summary 就要 150–200 词,同时每节还要至少 5 个来源。压力测试里又有 50 页以上的长报告。                                                               | 长度约束与内容要求矛盾,要么被截断,要么违反篇幅限制。                 |
| 12  | 权限  | 所有智能体共享可读写的 `ResearchState`,没有字段级权限。Writer 或 Researcher 都能改 `review_scores`。                                                                            | Reviewer 的评分可能被篡改,质量关卡可被绕过。                 |
| 13  | 权限  | Publisher 的导出工具里 `filename` 和 `template` 是自由字符串,没有校验。工具也没有声明写入目录限制。                                                                                     | 可能覆盖任意文件或路径穿越。恶意模板还有注入风险。                   |
| 14  | 风险  | "Researcher 需验证主张"和"来源核验"全靠 Prompt 约束,没有机制强制执行。`sources` 里只存了 `url`、`title`、`content`,没有可信度、访问时间等字段。                                                    | 幻觉引用、来源造假无法被发现。Reviewer 的"来源质量"评分缺乏依据。      |

## P2(8 项,规范性、可维护性和可观测性问题)

| #   | 类别  | 概要                                                                                                              | 可能影响                              |
| --- | --- | --------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| 15  | 缺陷  | 命名与路径不一致。角色叫 Revisor,文件却是 `reviser.py`。Prompt 里的"Reviewer"与 Schema 的 "review_tools" 也不统一。                       | 文档与代码难以对应,增加理解成本。                 |
| 16  | 缺陷  | 文中写"8 roles × 3 artifact types",实际有 8 个 Prompt、3 套 Schema 和 2 个配置,Human 并不是 Prompt 型工件。                         | 工件数量统计有误,评测口径混乱。                  |
| 17  | 缺陷  | `export_markdown`、`export_pdf`、`export_docx` 没有 HTML 导出,但 Publisher 声称支持 HTML。Schema 里的参数也没有写类型。                | 能力声明与实际工具不符,调用 HTML 导出会失败。        |
| 18  | 缺陷  | `web_search` 的 `source` 枚举只有 tavily/google/bing,而 `task.json` 的 `source` 是 `"web"`。文末又提到 MCP 检索,但 Schema 里没有定义。 | 配置到工具的映射不清晰,MCP 检索路径没有 Schema 支撑。 |
| 19  | 风险  | 错误处理只有 `error_log` 和一句"优雅处理"。没有重试策略、降级方案或失败状态,`current_phase` 也没有 `failed` 或 `cancelled`。                       | Human 选"取消"、研究失败等情形没有状态可落。        |
| 20  | 风险  | 没有成本、token、速率限制和并发上限。`run_research` 是并行的,且"模型 gpt-4o"写死在配置里。                                                    | 成本不可控,并发时可能触发 API 限流。             |
| 21  | 风险  | 没有审计与隐私要求。Human 节点的决策、`messages` 和 `sources.content` 全量留存,没有脱敏或保留期限定义。                                          | 难以追溯责任,可能留存敏感内容。                  |
| 22  | 缺陷  | 文档本身有两点不严谨。其一,评测量表只有空白的评分表,没有判定标准。其二,"最佳实践"的结论与上面发现的问题相矛盾。                                                      | 评测结果主观,可能误导使用者。                   |

## 总体结论

- **最该先处理的**:#1(默认批准)、#2(无限循环)、#3(路径穿越)、#4(提示注入)。
- **最影响可用性的**:#5–#9。Prompt、Schema 和 State 三处对工具名、评分格式、阶段定义各说各话。
- **局限**:本次只依据这份摘要文档,没有源码。部分问题,例如 #6、#7、#13,可能只是摘要省略了细节。如果能提供 `multi_agents/` 源码,我可以复核哪些问题属实。
