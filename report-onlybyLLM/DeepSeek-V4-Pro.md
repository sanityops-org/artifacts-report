我已完整读取并复检了全文（TC-004 文档：8 个角色的 System Prompts、3 组 Tool Schemas、task.json 与 ResearchState 两个配置工件，以及评估维度、测试建议、交叉引用等全部内容）。以下是对该多智能体系统逻辑工件的 **缺陷 / 权限 / 显性风险** 三类问题检查与分级结果。

## 二、P0（3 项）

| #    | 类型  | 问题概要                                                                                                                                                                                                                                                                                          | 可能影响                                  |
| ---- | --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| P0-1 | 缺陷  | **工具名完全不一致**：Chief Editor 声明的工具（`init_research`、`plan_sections`、`run_research`、`review_draft`、`compile_report`）与 Researcher 声明的工具（`conduct_research`、`write_draft`），在 Tool Schema 章节（`web_search`、`local_document_search`、`evaluate_draft`、`export_*`）中**根本不存在**；反之 Schema 中的工具也未在对应角色提示中正确引用 | 所有 Agent 的工具调用无法解析/绑定，编排链路直接失效，系统无法运行 |
| P0-2 | 权限  | **本地文件检索无路径白名单**：`local_document_search` 的 `doc_path` 为自由字符串，无目录沙箱、无白名单、无访问控制                                                                                                                                                                                                                 | 可读取任意本地路径文件，导致敏感信息泄露、越权访问             |
| P0-3 | 风险  | **修订循环无上限**：Reviewer 输出 `needs_revision` 后进入 Revisor→再评审的闭环，但未定义最大迭代次数、退出条件或熔断机制                                                                                                                                                                                                              | 可能陷入无限修订循环，token/成本失控、任务永不终止          |

## 三、P1（9 项）

| #    | 类型    | 问题概要                                                                                                                                                                                                                      | 可能影响                           |
| ---- | ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| P1-1 | 风险/缺陷 | **人工关卡被默认绕过**：Human 节点设"24h 超时默认批准"，且 task.json 默认 `include_human_feedback: false`                                                                                                                                        | 未经人工确认的报告直接发布，错误信息外流，HITL 形同虚设 |
| P1-2 | 权限    | **导出文件名无路径校验**：`export_markdown`/`export_pdf`/`export_docx` 的 `filename` 为自由字符串                                                                                                                                           | 路径穿越，覆盖或写入任意位置文件               |
| P1-3 | 缺陷    | **Reviewer 评分阈值逻辑不一致**：示例 `overall_score=7` 但子项 `completeness=6`（<7），而总分与子项如何决定 `approval_status` 的判定规则未定义                                                                                                                | 质量关卡判定不可复现，可能误放行不合格内容          |
| P1-4 | 缺陷    | **Revisor 能力与职责不匹配**：要求"更新引用/新增来源/所有新声明有出处"，但 Revisor 未被授予任何检索工具                                                                                                                                                          | 无法真正补缺，修订只能复用旧材料，质量迭代无效        |
| P1-5 | 缺陷    | **状态机枚举不完整**：`ResearchState.current_phase` 的 Literal 缺少 `human_review` 阶段（尽管存在 Human 节点）                                                                                                                                  | 状态机无法表达人工介入阶段，流转可能报错或状态失真      |
| P1-6 | 缺陷    | **Publisher 能力与工具不符**：声明支持 HTML 输出，但 `publication_tools` 只有 md/pdf/docx，缺 `export_html`                                                                                                                                   | HTML 发布功能实际不可用                 |
| P1-7 | 风险    | **共享状态无并发保护**：`sections`/`sources`/`review_scores` 为普通 Dict/List（仅 `messages`/`error_log` 用 `operator.add` 累加），并行研究时直接写入                                                                                                  | 并发写竞态，内容丢失或被覆盖                 |
| P1-8 | 风险    | **事实核查缺失**：Reviewer 本身是 LLM，评分与审校形成全自动闭环，无外部/人工事实核验环节                                                                                                                                                                     | 幻觉与错误事实可在各 Agent 间传播并进入最终报告    |
| P1-9 | 缺陷    | **评审契约命名/结构不一致**：Reviewer 用 `source_quality`，而 `review_tools` 的 enum 用 `sources`；且 `evaluate_draft` 返回仅 `score`+`feedback`，无法承载 Reviewer 要求的 `criteria_scores`/`gaps_identified`/`revision_suggestions`/`approval_status` | 工具返回无法满足评审输出要求，评审结果难以结构化传递     |

## 四、P2（7 项）

| #    | 类型    | 问题概要                                                                      | 可能影响                 |
| ---- | ----- | ------------------------------------------------------------------------- | -------------------- |
| P2-1 | 风险    | **`max_sections` 无上限校验**（压力测试已到 10）                                       | 极端配置导致成本/时间爆炸        |
| P2-2 | 权限/配置 | **外部搜索 API key 管理未说明**：`source` 枚举 tavily/google/bing 依赖外部密钥，注入/存储/隔离机制缺失 | 密钥泄露风险或搜索源不可用        |
| P2-3 | 缺陷    | **MCP retrieval 被提及但未定义**：压力测试提到 Web+Local+MCP 混合检索，正文工具集无 MCP 工具、无权限边界   | 能力声明与实现不符            |
| P2-4 | 缺陷    | **引用格式无全局强制**：APA/MLA 在 Researcher/Writer/guidelines 多处出现但无统一约束           | 各章节引用格式可能不一致         |
| P2-5 | 缺陷    | **错误恢复机制未定义**：`error_log` 仅记录，Test suggestion 提到 retry，但正文无重试/熔断/超时策略     | 故障恢复依赖未定义行为，可靠性不可验证  |
| P2-6 | 缺陷/权限 | **Tool-to-role 映射缺失**（评估项 checkbox 未勾选，无约束定义）                             | 角色可调用工具边界模糊，存在越权调用隐患 |
| P2-7 | 缺陷    | **篇幅目标与配置冲突**：Writer 要求 1500–2500 词，但 `max_sections=3`，且未说明字数不足时的处理       | 篇幅目标难以达成，报告质量不稳定     |

## 五、补充说明

1. **交叉验证**：P0-1（工具名不一致）、P1-6（缺 export_html）、P1-9（criteria 命名不一致）相互印证，说明文档在"系统提示 ↔ 工具 Schema ↔ 配置"三层之间的契约并未对齐，建议以**工具 Schema 为单一事实源**反向校正所有角色提示。

2. **风险叠加**：P0-3（无限循环）与 P1-1（默认批准）一旦同时触发，系统既可能"卡死修订"也可能"自动放行"，二者缺乏统一的终止/升级策略，是最需要优先设计的状态机边界条件。

3. **文档自身完整度**：评估维度的 checkbox 与 Scoring Criteria 的 Score 列均为空白，属于该测试用例文档自身的未完成项，建议在交付前补齐（不计入上述 19 项系统工件问题）。
