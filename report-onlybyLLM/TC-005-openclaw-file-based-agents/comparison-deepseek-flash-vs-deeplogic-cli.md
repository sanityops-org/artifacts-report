# TC-005：直接模型评测 vs deeplogic-cli 评测对比

- **对比对象 A**：[`DeepSeek-FLASH.md`](./DeepSeek-FLASH.md)（直接由模型完成评测）
- **对比对象 B**：[`deeplogic-cli.md`](./deeplogic-cli.md) / [`deeplogic-cli.inspect-raw.md`](./deeplogic-cli.inspect-raw.md)（deeplogic-cli 实测）
- **对比日期**：2026-10-20
- **被测文件**：`test-cases/agent-suite/TC-005-openclaw-file-based-agents.md`

---

## 一、结论摘要

1. **定性结论一致**：两种方式都认为 TC-005 存在严重缺陷，当前不适合直接作为生产级多智能体配置使用。
2. **覆盖重点不同**：直接模型重点审查六类 Markdown 工件之间的语义、路由、隔离和生命周期一致性；deeplogic-cli 重点按 QDP 固定规则检查 Prompt 契约、输入输出、安全边界和可测试性。
3. **发现数量不同**：
   - 直接模型：26 项（P0 4 / P1 12 / P2 10）
   - deeplogic-cli：18 项 LLM 缺陷（P0 10 / P1 7 / P2 1），另有 2 项 QC Lint P1
4. **分数不能直接横向排名**：
   - 直接模型采用 TC-005 自带的六维加权表，得分 **2.1 / 5（约 42 / 100）**。
   - deeplogic-cli 使用 QDP 规则计分，得分 **52.63 / 100，等级 C，门禁 FAIL**。
   - 两者评分体系、输入粒度和严重级别定义不同，不能据此得出“CLI 认为质量更高”的结论。
5. **高置信共性问题**：两个报告在至少 8 个主题上形成交叉确认，包括文件类型数量矛盾、路由关系不闭合、工具与 Skill 契约不足、外部动作缺少约束、用户/记忆数据风险、输出与验收标准不足、Markdown 结构问题及运行频率治理。
6. **最适合各自的任务**：
   - 完整 Agent 套件的语义与跨文件审查：直接模型当前覆盖更完整。
   - 固定规则的回归检查、CI 门禁和缺陷定位：deeplogic-cli 更标准化、可重复。
   - 最佳实践是两者组合，而不是用其中一个完全替代另一个。

## 二、评测口径对比

| 对比项 | DeepSeek-FLASH 直接评测 | deeplogic-cli 评测 |
|---|---|---|
| 输入理解 | 将文件理解为完整 Agent 套件，并区分 SOUL、AGENTS、USER、IDENTITY、HEARTBEAT、MEMORY | 本次配置将完整 Markdown 注册为 **1 个 Prompt 工件** |
| 工件粒度 | 六类文件分别分析，同时做跨文件关联 | 0 Tool、0 Skill、1 Prompt |
| 评测方法 | 根据 TC-005 自带的六维评估框架自由评审 | deeplogic-cli L2 + QDP/QD-PM + QC Lint |
| 规则来源 | 模型自行组织检查项和分级 | 固定 QD/QDP/QC 规则集 |
| 跨工件检查 | 有人工式语义关联，覆盖路由、命名、文件和权限一致性 | 缺少独立的多工件组合，CROSS 结论不可用 |
| 权限检查 | 对 Shell、用户资料、Agent 隔离及外部外联做风险分析 | QD-PM 因 Gate-0 前置条件失败而跳过 |
| 可重复性 | 中等；受提示、模型采样和对套件结构的理解影响 | 较高；规则、级别、定位和输出结构固定 |
| 证据形式 | 工件位置 + 影响 + 修复建议 | 规则 ID + 严重级别 + 位置 + 影响 + 修复建议 |
| 评分方式 | 20/15/20/20/15/10 六维加权，1–5 分 | QDP 规则得分 52.63/100，等级 C |
| 最终门禁 | 定性结论为需要重点修复，未给出二值门禁 | Gate FAIL |
| 执行时间 | 未记录 | 291.62 秒 |

### 口径差异的影响

deeplogic-cli 的 QDP 检查面向单个 Prompt。把整个 TC-005 文档作为一个 Prompt 提交后，CLI 会把“测试文档没有任务说明、输入格式和输出 Schema”当成 Prompt 缺陷；这些结论作为“完整套件规范不足”是成立的，但其中一部分也来自**测试容器与 Prompt 对象之间的表示差异**。

直接模型则能识别文档内部的六个示例文件，因此更容易发现 YAML 注释键、渠道声明矛盾、Agent 命名路径不一致、语言策略冲突和跨 Agent 权限问题。这解释了为什么直接模型在“套件结构类”问题上覆盖更广。

### 为什么 CLI 的分数更高、P0 却更多

这并不矛盾：

- CLI 的 52.63 分来自 QDP 规则扣分模型，关注的是已配置 Prompt 的规则命中情况。
- 直接模型的 2.1/5 是按套件总体成熟度给出的主观加权分，同时纳入了配置、隔离、可审计性和可扩展性。
- CLI 本次没有真正执行完整的 Tool/Skill/CROSS/QD-PM 检查，因此其 52.63 分不能代表整个 OpenClaw 套件的综合质量。
- 因此，两份分数只能分别用于各自体系内判断，**不具备直接可比性**。

## 五、直接模型独有或明显更强的发现

DeepSeek-FLASH 在完整套件语义方面覆盖更广，以下内容没有被 CLI 报告同等程度地检出或定位：

1. **渠道路由 YAML 解析问题**：`#support`、`#sales` 会被 YAML 当作注释，Telegram 的 `@...` 纯量也存在兼容性风险。
2. **渠道声明与路由表矛盾**：`sales-assistant` 声明 WhatsApp/Email，却出现在 Telegram/Slack 路由中；部分渠道没有绑定。
3. **Agent 命名和文件路径不统一**：`support-main`、`customer-support-agent`、`Helper`、`support-soul.md`、`SOUL.md` 之间缺乏权威映射。
4. **语言策略冲突**：SOUL 强制英文，而 USER 标明 Mandarin 母语和详细解释偏好，没有优先级或例外。
5. **Handoff 契约不完整**：缺少上下文传递、接收确认、拒绝、超时、回退和防循环规则。
6. **长期记忆可被污染**：缺少来源证明、写入权限、过期、冲突处理和删除机制。
7. **外部内容的数据/指令边界缺失**：知识库、文件、用户资料和记忆中的文本未明确标记为不可信数据。
8. **多 Agent 隔离没有可审计配置**：没有 workspace、state path、ACL 或跨 Agent 访问策略。
9. **时间语义不明确**：`yesterday 18:00`、`< 3 days ago` 等条件缺少时区、格式和边界定义。
10. **可观测性与测试可执行性不足**：缺少路由、交接、工具调用、记忆写入和定时任务审计；测试建议没有输入、预期结果和失败判定。
11. **版本可追溯性不足**：缺少固定 Commit SHA、逐文件源码 URL 和完整采集路径。

这些发现说明：对于“文件驱动多智能体套件”，仅检查一个聚合 Prompt 不足以完整识别配置关系中的矛盾和权限边界。

## 六、deeplogic-cli 独有或明显更强的发现

deeplogic-cli 的规则化检查在以下方面更明确：

1. **任务边界缺失**：未说明最终应输出评测、评分、测试还是总结，QDP 判为 P0。
2. **输入来源与输入格式缺失**：没有声明渠道事件载荷、字符集和长度限制，分别判为 P0。
3. **输出格式与输出 Schema 不完整**：评分表、最终报告字段和汇总方式未定义，判为 P0。
4. **对话/任务终止条件缺失**：没有明确何时停止处理。
5. **负例覆盖不足**：只有语气负例，缺少路由、安全、工具和输出负例。
6. **边界条件示例不足**：缺少空输入、超长输入、未知意图和缺失配置示例。
7. **评测标准含不可操作措辞**：`clear`、`reasonable`、`appropriate` 没有量化定义。
8. **代码块语言标识缺失的精确位置**：QC 直接给出行号 140 和 258。
9. **统一缺陷结构**：每条缺陷都有规则 ID、位置、影响和修复建议，适合作为工程工单或 CI 输出。

## 七、严重级别冲突与人工裁决建议

| 问题 | DeepSeek-FLASH | deeplogic-cli | 差异原因 | 建议裁决 |
|---|---|---|---|---|
| 路由目标未注册 | P0 | P2 | 直接模型按完整套件可用性判断；CLI 按单 Prompt 中“不可达条件”判断 | **完整套件口径下应优先按高严重级别处理**，至少 P1，若消息确会进入该路由则应为 P0 |
| 核心文件类型数量矛盾 | P2 | P0 | 直接模型视为范围说明问题；CLI 视为核心约束直接冲突 | 建议 **P1**：会误导模型和加载器，但通常不等于整个系统不可用 |
| HEARTBEAT 依赖未声明 | P1 | P0 | 直接模型将其视为执行失败风险；CLI 视为未声明资源/工具 | 建议 **P1–P0**，取决于定时任务是否属于主流程；若属于核心外联流程则按 P0 |
| 输出与验收契约不足 | P2（拆分项） | P0（合并项） | CLI 对 Prompt 输出契约采用更高权重 | 建议 **P1**；若该文件要直接充当系统提示词，则 P0 合理 |
| Shell 与外联安全边界 | P0 | P0 | 两个体系的严重级别一致 | 保留 **P0** |
| 权限隔离 | P0/P1 | 因上游 P0 跳过 | CLI Gate-0 未执行权限检查 | 不能因 CLI 跳过而降低风险，应保留直接模型的隔离发现 |

**严重级别不能直接取平均。** 应先确定评测对象究竟是：

- “完整 Agent 套件的配置文件集合”，还是
- “一份将被直接注入模型的单个 System Prompt”。

TC-005 的真实对象是前者，但它目前被压缩成单文件展示。CLI 的输入适配因此会影响部分严重级别和覆盖范围。

## 九、哪种评测方式更合适

### 适合 DeepSeek-FLASH 的场景

- 首次审查完整 Agent 套件。
- 需要理解角色边界、路由、交接、记忆和多文件一致性。
- 需要发现“规则未显式写出，但跨文件组合后会出错”的问题。
- 需要给出面向架构和产品风险的综合判断。

### 适合 deeplogic-cli 的场景

- 在 CI 中设置稳定质量门禁。
- 对 Prompt 的输入、输出、安全、终止、示例和格式做固定规则检查。
- 需要统一缺陷 ID、位置、严重级别和修复建议。
- 需要跨版本回归，比较同一工件是否新增或修复了特定规则问题。

### 推荐的组合流程

1. **先用 deeplogic-cli 做快速、可重复的基线门禁**，捕获明确的 QDP、Tool、Skill 和 QC 问题。
2. **拆分 TC-005 内部的六类工件**，分别注册为 Prompt/Skill/Tool 或适合的工程对象，再重新运行 CLI，以启用真正的跨工件检查。
3. **再用模型做完整套件复核**，重点检查路由、命名、渠道、交接、记忆、权限和生命周期。
4. **统一严重级别口径**后做人工裁决，重点复核 P0 冲突项。
5. **合并去重后形成唯一修复清单**，避免按两个报告的原始数量直接累加。

## 十、最终判断

### 一致结论

两种评测方式都支持以下判断：

> TC-005 具有清晰的“文件驱动 Agent”设计方向，但当前配置在路由闭环、工具与 Skill 契约、安全边界、用户与记忆隔离、输出与验收标准方面存在重大缺口，不能直接作为可靠的生产级 Agent 套件。

### 主要差异

- **直接模型更全面**：尤其擅长跨文件语义、配置矛盾和运行风险推理。
- **deeplogic-cli 更标准化**：规则明确、定位精确、便于自动化和 CI。
- **CLI 的覆盖并不完整**：本次仅检查 1 个 Prompt，权限检查被阻断，跨工件结论不可用。
- **直接模型的严重级别不够统一**：部分问题偏重、部分问题偏轻，更适合作为风险线索而不是唯一门禁。

### 推荐结论

如果必须在两者中选择：

- **评价完整 TC-005 套件的语义质量**：优先采用 DeepSeek-FLASH 的完整套件视角。
- **建立工程化质量门禁**：优先采用 deeplogic-cli。
- **正式评测或发布前**：采用“CLI 基线门禁 + 模型跨工件复核 + 人工严重级别裁决”的组合方式。
