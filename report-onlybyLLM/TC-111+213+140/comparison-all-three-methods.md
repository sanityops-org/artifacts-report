# TC-111+213+140 三方法评测对比总报告

> **更新时间**：2026-10-21
> 本版已按新版 `综合评测报告.md` 重写。新版直接模型报告已从“逐用例缺陷清单”调整为“三工件组合缺陷、权限与风险检查”，旧版 59.0 / 64.5 / 58.0 分和 28 项缺陷的统一计数不再适用。

## 1. 范围与方法

本报告对比三种独立评测方法对同一批工件的结果：

1. **直接模型评测**：`综合评测报告.md`。基于逐用例维度评分、Draft-07 元校验、代表性输入验证、权限矩阵和跨工件威胁建模。
2. **deeplogic-cli 评测**：QDP/QDT/QDS 规则、QC lint、缺陷分级和质量门禁。三件工件分别独立运行。
3. **sanityops-inspect-lite 评测**：SanityOps 框架规则包、Gate-0 结构门禁、Risk Explicit 审计和影响展望。三件工件分别独立运行。

三者的评测单元并不相同：

- 直接模型报告评价的是**单工件质量与三工件组合风险**。
- `deeplogic-cli` 与 `sanityops-inspect-lite` 主要评价**单工件结构和规则缺陷**。
- 当前 CLI 和 lite 的三个运行都没有在同一个上下文中载入完整三工件闭环，因此不能替代直接模型的组合分析。

- 直接模型：三工件组合后存在本地数据读取、外部网络访问、第三方发送、付费调用和自动外联链，**不建议原样组合上线**。
- deeplogic-cli：TC-111 FAIL、TC-213 PASS、TC-140 FAIL，整体仍不能视为通过。
- sanityops-inspect-lite：三件工件均未通过 Gate-0，整体不能视为通过。

## 4. 逐工件对比

### 4.1 TC-111 SalesGPT System Prompt

#### 三种判断

**直接模型：3.55 / 5（71%）**

- 角色和流程可理解，但同意、退订、来源真实性、工具兼容性和异步状态契约不足。
- 来源问题同时作为 R-03 和 R-06 的组合风险出现。
- 与其他工件的组合暴露出字符串 `Action Input` 与对象工具参数不兼容、异步 job ID 与一次性 Observation 流程不兼容。

**deeplogic-cli：89.22 / B / FAIL**

- QDP-1.1.1 P0：首轮问候规则与 Introduction 阶段冲突。
- QDP-1.3.2 P1：“short length”不可度量。
- QDP-2.3.1 P1：`<END_OF_CALL>` 格式未闭合。
- QC 还有 2 项 P1：代码块缺少语言标识。

**sanityops-inspect-lite：Gate-0 Not passed，2 P0 / 8 P1 / 3 P2**

- 与 CLI 共同发现首轮冲突、模糊长度和终止令牌问题。
- 额外发现 QD-P-2.5.2 P0：“public records”来源话术构成欺骗性来源风险。
- 额外发现工具异常、降级策略和身份强化等 EX 风险。

#### 对比结论

- CLI 与 lite 在 Prompt 结构缺陷上高度一致。
- 直接模型与 lite 更重视销售合规和来源真实性；CLI 没有检出“public records”P0。
- 直接模型独有的组合分析指出 Action Input 和异步工具状态不兼容，但这不属于单一 Prompt 规则能完整覆盖的问题。

### 4.2 TC-213 Firecrawl MCP Tool Schema

#### 三种判断

**直接模型：2.65 / 5（53%）**

该工件自身确认 5 项缺陷：

- F-01 严重：`schema` 参数无法接收非空 JSON Schema。
- F-02 高：跨字段约束只写在描述中，Schema 不执行。
- F-03 高：声称存在 `outputSchema`，实际快照中没有。
- F-06 高：URL 范围缺少协议、数量和目标控制。
- F-09 中：核心参数缺少描述，`maxCredits` 上限不合理。

同时参与：

- F-04 高：字符串 Action Input 与对象工具参数不兼容。
- F-05 高：异步 job ID 与一次性 Observation 流程不兼容。

**deeplogic-cli：100.00 / A / PASS，0 缺陷**

- 认为描述、基础 JSON Schema 结构、枚举和风险注解完整。
- 未检出 `schema` 空壳、跨字段约束、UUID 占位符、URL 协议限制或 `outputSchema` 缺失。

**sanityops-inspect-lite：Gate-0 Not passed，0 P0 / 2 P1 / 3 P2**

- QD-T-4.1 P1：`schema` 描述不足。
- QD-T-4.7 P1：没有 `outputSchema`。
- QD-T-2.5 P1：`maxCredits` 缺少单位/货币语义。
- QD-T-1.4 P2：`schema` 的 `additionalProperties: false` 可能拒绝有效模式。
- QD-T-3.2 P2：`urls` 接受任意 URI，缺少域名白名单。
- EX 额外发现开放网络、默认付费和 URL 范围控制风险。

#### 对比结论

这是三种方法分歧最大的工件：

1. 直接模型通过具体实例证明 `schema` 和跨字段约束存在功能缺陷，并给出最高严重度。
2. lite 也检出 `schema` 结构和 `outputSchema` 问题，但严重度明显更低。
3. CLI 给出 100/A/PASS，属于单工件 L1 的明显漏报。

因此，TC-213 不能依据 CLI 分数判定为生产可用。直接模型的实例验证应作为主要裁决证据，lite 结果可作为可重复的辅助发现。

### 4.3 TC-140 CSV Data Summarizer Skill

#### 三种判断

**直接模型：2.80 / 5（56%）**

- F-07 高：强制自动执行，缺少敏感数据和大文件闸门。
- F-08 中：日期识别和“优雅处理缺失数据”缺少实现依据。
- R-01 严重：CSV → 模型上下文 → Firecrawl 的本地数据外泄链。
- R-02 严重：CSV 和网页内容可形成提示注入链。
- R-05 高：自动分析结果可能被包装为不可靠的业务结论。

**deeplogic-cli：20.55 / D / FAIL，5 P0 / 11 P1**

主要 P0：

- 输入规模和文件边界缺失。
- 执行资源、重试和超时边界缺失。
- 全面分析无上限。
- 非目标范围缺失。
- 失败处理策略缺失。

**sanityops-inspect-lite：Gate-0 Not passed，5 P0 / 10 P1 / 2 P2**

- 与 CLI 在输入、资源、无界分析、non-goals 和失败处理上高度一致。
- 额外进行 Risk Explicit 审计，将“DO NOT ASK THE USER”识别为 Explicit·P0 约束移除。
- 给出资源耗尽、权限扩张和异常传播等影响卡片。

#### 对比结论

- CLI 与 lite 的 TC-140 结论高度一致，且都明显严于直接模型的 56% 分数。
- 这并不表示两种工具一定更准确，而是因为它们的规则直接覆盖资源、权限和失败边界，而直接模型的自带维度更偏工件设计质量。
- 直接模型补充了单工件评估看不到的组合数据流风险：本地 CSV 经模型进入外部 Firecrawl provider，形成数据外泄和提示注入路径。

|---|---|---|---|

| 原始执行证据 | 中 | **高** | 中 |
| 分数计算 | 有，逐工件维度分 | **有，等级和门禁** | Gate-0 未通过时无 |
| 零安装 | 是 | 否 | **是** |
| 跨方法一致性 | 低 | 中 | 中高 |

### 5.1 各自优势

**直接模型评测**

- 唯一真正执行三工件组合威胁建模的方法。
- 通过 Draft-07 元校验和代表性输入验证发现 CLI 漏掉的 Schema 功能缺陷。
- 能解释数据流、权限链、成本审批和销售合规之间的组合影响。

**deeplogic-cli**

- 规则应用标准化，输出分数、等级、P0/P1/P2 和门禁。
- 保留配置、控制台日志、原始报告和工件副本，便于追踪。
- 适合 CI/CD 回归和大规模工件的一致化基线。

**sanityops-inspect-lite**

- 规则覆盖最完整，包含 Gate-0 和 Risk Explicit 审计。
- 对约束移除、权限扩张、开放网络和默认付费等风险表达有额外识别能力。
- 零安装，适合较早阶段的深度静态审查。

### 5.2 各自局限

**直接模型评测**

- 新版的分数、确认缺陷和组合风险不是统一的可加总模型。
- 不容易完全复现同一判断，需要保存 prompt、模型版本和验证脚本。

**deeplogic-cli**

- TC-213 的 100/A/PASS 是明显假阴性。
- L1 深度不足，L2 又受超时影响。
- 三件工件分别运行，无法看到组合攻击面。

**sanityops-inspect-lite**

- Gate-0 未通过时不提供分数，不利于直接排序。
- 报告由 host model 执行，存在模型解释和计数口径漂移。
- EX 项与 Stage A 缺陷在附录中可能混排，需要仔细区分。

## 7. 推荐使用方式

### 发布前组合审查

优先使用**直接模型报告**。它覆盖组合攻击面、数据外泄、提示注入、工具异步契约和销售合规，是当前唯一真正回答“三个工件能否安全组合”的方法。

### CI/CD 与回归门禁

使用 **deeplogic-cli**。它适合作为可重复的单工件门禁，但不应把 TC-213 的 100 分当作最终发布批准。

### 深度规则与风险审计

使用 **sanityops-inspect-lite**。它适合识别约束移除、权限扩张、Gate-0 结构缺口和风险表达，但需要人工复核计数口径和 Gate-0 条件。

### 推荐组合流程

1. 用 sanityops-inspect-lite 做完整静态规则和 EX 风险审计。
2. 用 deeplogic-cli 做标准化门禁和回归记录。
3. 用直接模型做组合威胁建模和具体 Schema 反例验证。
4. 对三者分歧项进行人工裁决，尤其是 TC-213。

## 9. 最终结论

三种方法不是互相替代关系：

- **直接模型**最强于组合风险、Schema 语义和权限/合规推理。
- **deeplogic-cli** 最强于可重复门禁、标准化分级和执行证据。
- **sanityops-inspect-lite** 最强于完整规则覆盖、Gate-0 和 Risk Explicit 审计。

本轮结果最重要的教训不是“哪个工具总分更高”，而是：

1. CLI 的 100 分不能证明 TC-213 的契约正确。
2. 单工件检查看不到组合数据流风险。
3. 直接模型的高语义覆盖率需要标准化证据和人工复核来固定结论。
4. 最终发布决策应采用“lite 深度审计 + CLI 回归门禁 + 直接模型组合审查”的三层流程。
