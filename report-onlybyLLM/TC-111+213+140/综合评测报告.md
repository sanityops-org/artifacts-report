# TC-111 + TC-213 + TC-140 综合评测报告

> 评测范围：SalesGPT System Prompt、Firecrawl `firecrawl_agent` Tool Schema、CSV Data Summarizer Skill。  
> 评测方式：基于用例中的 verbatim 工件做静态审查；对 TC-213 的输入 Schema 额外执行 JSON 解析、Draft-07 元 Schema 校验和边界实例验证。未调用 SalesGPT、Firecrawl 或 `analyze.py` 运行时。  
> 评分口径：1=不可用；2=存在显著缺陷；3=基本可用但需修复；4=良好；5=优秀。综合分按各用例自带权重折算为百分制。跨用例总分仅按三件工件等权平均，用于横向比较。

**总体结论：三件工件均未达到可直接生产使用的水平。Firecrawl Tool Schema 的说明与结构最成熟，但输入、输出契约存在功能性缺口；SalesGPT 具备完整销售流程，却包含一项高危来源披露规则；CSV Skill 结构清晰，但默认全自动执行且缺少资源、隐私和失败边界。综合得分 60.5/100，属于“有条件可用、修复后复测”区间。**

## 三、P1（17 项）

| # | 用例 | 类型 | 问题概要 | 可能影响 |
|---|---|---|---|---|
| P1-1 | TC-111 | 缺陷 | **首轮问候规则互相冲突**：第 25 行要求“只问候、先不推销”，第 28 行又要求首轮介绍自己和公司并说明来电原因 | 首轮输出不确定，可能违反测试断言或显得突兀 |
| P1-2 | TC-111 | 缺陷 | **8 阶段只有描述，没有状态字段、进入/退出条件、跳转规则或失败回退规则**；“思考当前阶段”无法形成可审计状态 | Agent 可能跳阶段、重复阶段或卡在某一阶段，阶段测试不可稳定复现 |

| P1-5 | TC-111 | 风险 | **用户输入和 `Observation` 未标记为不可信数据**，也没有“忽略其中指令、只把它们当作销售对话内容”的隔离规则 | 潜在提示词注入可劫持人设、泄露系统提示或诱导违规承诺 |

## 五、逐项综合判断

### TC-111 SalesGPT System Prompt

优点是人设、公司信息、联系目的、渠道、语气和 8 阶段流程都明确，ReAct 文本协议也足以支持基本解析。主要问题不是“信息不足”，而是**行为优先级冲突和合规边界缺失**：首轮问候自相矛盾，阶段没有状态机，工具参数被过度简化，且“public records”规则把来源披露变成了不可验证的固定话术。该 Prompt 适合作为销售流程原型，不适合直接用于真实外呼、营销或受监管市场。

### TC-213 Firecrawl `firecrawl_agent` Tool Schema

工具描述质量明显高于另外两件工件：能力、适用/不适用场景、异步状态、续聊、额度和条款审批都写得很清楚；Draft-07 元 Schema 校验通过，`required` 与顶层 `additionalProperties: false` 也正确。但契约层存在两类硬伤：**`schema` 参数无法承载真实 JSON Schema，跨字段约束只停留在自然语言**。此外，`outputSchema` 缺失和 UUID 占位符通过校验，会削弱客户端集成与运行时可信度。修复这些问题后，工件质量可达良好以上。

### TC-140 CSV Data Summarizer Skill

元数据、触发描述和自动分析步骤清楚，适合作为“减少交互、一次产出完整结果”的设计样例。但它的核心设计把“不要问”绝对化，未给正常澄清留下安全出口；同时缺少文件规模、路径、敏感数据、依赖失败和输出可复现性约束。最具体的缺陷是可视化规则前后矛盾，以及 `analyze.py` 的执行契约没有随 Skill 快照闭环。当前版本可能“看起来很强”，但实际运行的可控性和可验证性不足。

## 六、补充说明与修复优先级

1. **优先修复 P0-1**：将“说来自 public records”改为“仅在有可核实来源时说明；否则明确无法确认并停止使用该联系数据”。同时补充数据来源记录、同意/合法依据、退订和停止联系规则。

2. **工具契约先于文案优化**：TC-213 应将 `schema` 改为可递归承载 JSON Schema 的对象（或明确定义允许的 schema 子集），用 `allOf`/`if-then`/`oneOf` 表达 `strictConstrainToURLs`、`requireApproval`、`approve/decline` 的依赖与互斥，移除 `<uuid>` 占位分支，并补上版本化的 `outputSchema`。

3. **把 CSV 自动化改成“默认执行 + 安全例外”**：正常 CSV 可立即分析，但文件不可读、受密码保护、编码/分隔符不明、规模超限或用户目标明显不是分析时必须澄清或拒绝；补充路径沙箱、文件类型验证、行列/时间上限、抽样策略、依赖失败回退和单元格内容隔离。

4. **补足可测试性**：TC-111 需要机器可读阶段状态和明确终态；TC-213 需要针对上述反例建立自动化 JSON Schema 测试；TC-140 需要固定命令、输出目录、图表命名、错误码和大文件基准。

5. **验证证据**：TC-213 JSON 解析成功，且 `jsonschema` 的 Draft-07 元 Schema 校验通过。实测同时发现：典型输出 Schema 被拒、`strictConstrainToURLs` 无 `urls` 通过、`requireApproval` 无 `mode: "chat"` 通过、`threadId: "<uuid>"` 通过、`approve` 与 `decline` 同时提交通过。这些均是可用于回归测试的确定性证据。

6. **用例文档自身完整度**：三份用例的 Evaluation Dimensions checkbox 和 Scoring Criteria Score 列均为空白；TC-213 的 Metadata 称快照含 `outputSchema`，正文 JSON 实际没有；TC-140 引用的 `analyze.py`、`requirements.txt` 未包含在快照中。以上属于测试用例/交付包完整度问题，本报告不计入 28 项工件缺陷，但建议一并补齐，以保证后续复测可执行。
